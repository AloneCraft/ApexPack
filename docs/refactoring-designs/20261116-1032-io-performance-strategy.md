# ApexPackの媒体別シリアライズ高速化設計案

## 背景

ネットワーク、SSD、HDD、メモリでは、CPU処理、コピー、I/O待ちの割合が異なる。メモリ上のシリアライズが速くても、全体を一時バッファに溜める経路では、大きなデータほど最初の復元までの待ち時間とピークメモリが増える。

## 現状の観察

- `SerializeAsync(Stream)` は結果全体を `byte[]` に作ってから書く。一般の `DeserializeAsync(Stream)` は末尾まで `MemoryStream` に読み込む。バッファを公開する `MemoryStream` には、既存領域を読み、消費した分だけ位置を進める経路がある。 [ApexPackSerializer.cs](../../src/ApexPack.Core/ApexPackSerializer.cs#L163)
- `IBufferWriter<byte>` への直接書き込みがある。複数セグメントの `ReadOnlySequence<byte>` は、全体をプールした連続領域にコピーしてから復元する。 [ApexPackSerializer.cs](../../src/ApexPack.Core/ApexPackSerializer.cs#L148) · [分割入力の実装](../../src/ApexPack.Core/ApexPackSerializer.cs#L196)
- 固定長配列は本体全体の連続領域を要求する。書き込み先をPipeにしても、この経路では大きな連続領域が必要になる。MemoryPack互換層のストリームAPIも、要素やバイト列を全体分保持する。 [配列フォーマッタ](../../src/ApexPack.Core/Formatters/ApexSequence.cs#L54) · [MemoryPack互換層](../../src/ApexPack.MemoryPackCompat/Extras.cs#L10)

## 過去設計から引き継ぐ仕様

ApexPack v2のバイト列、既存の公開APIの挙動、nullと空の区別、長さ・割り当て上限、必要なエンディアン変換を互換性の条件とする。参照保持を有効にした値では、共有参照と循環参照を同一のルートの中で復元する。対象は .NET 9・10・11。 [既存のアーキテクチャー案](20261116-0721-simpler-architecture.md#過去設計から引き継ぐ仕様) · [ワイヤ形式](../WireFormat.md)

## 目的

メモリでは余分なコピーと割り当てを減らす。通信とファイルでは、書き込み開始から読み手の復元完了までの時間を短縮し、同時に保持するデータ量を抑える。長時間接続では、接続を開いたまま複数の値を順番に受け取れるようにする。

## 非目的

試作の範囲は既存の型とバイト列を使う読み書きの経路。圧縮付きフレームや索引付きファイルの仕様決定は、それぞれを必要とする利用例の測定後に扱う。

## 提案設計

| 用途 | 戦略 | 主な指標 |
| --- | --- | --- |
| メモリ | 再利用できる `Span<byte>` や `IBufferWriter<byte>` へ直接書く。連続入力は `ReadOnlySpan<byte>` から読む | 処理時間、割り当て量 |
| ネットワークの小さいメッセージ | 長さ付きで1件ずつ解釈する。応答を急ぐときは早めに送り、大量に送るときは小さいメッセージをまとめる | 最初の1件の遅延、p95、送信回数 |
| ネットワークの大容量転送 | バッファに上限を設け、受信と復元を重ねる。帯域が詰まる条件で高速圧縮を比較する | 転送完了時間、転送量、ピークメモリ |
| SSD・HDDの全件処理 | 連続したブロックで読み書きし、次の読み込みを復元と重ねる。HDDでは離れた位置へのアクセスを抑える | 全件の完了時間、ピークメモリ、永続化までの時間 |
| SSD・HDDの部分取得 | 索引で必要な範囲を特定する。HDDでは近い読み出し範囲をまとめる | 取得までの時間、読み出し量 |

1. **直接書き込みと分割入力のコピー削減。** 既存の `IBufferWriter<byte>` 経路を比較に使う。読み取りの試作は `byte[]` と `int[]` を対象とし、検証済みの件数で最終配列を確保して入力セグメントから直接移す。raw layoutとリトルエンディアンの条件を満たす場合に一括コピーする。要素境界にまたがるデータとエンディアン変換が必要なデータは、既存フォーマッタと同じ結果になる経路で読む。
2. **長さ付きフレーム。** フレーム本体にはApexPack v2のバイト列を使う。可変長の本体はプールしたバッファへ1回書いて長さを確定する方式から試す。受信側は長さの上限を先に検証し、完全な1件だけを呼び出し元へ返す。大きなフレームは受信済み部分を順次消費できる構成にし、Pipeの流量制御と組み合わせる。外部からの入力には、フレーム上限と既存の逆直列化の安全上限を両方適用する。 [System.IO.Pipelinesの流量制御](https://learn.microsoft.com/en-us/dotnet/standard/io/pipelines#backpressure-and-flow-control)
3. **圧縮とファイル索引。** 圧縮で減ったI/O時間が圧縮・展開時間を上回る条件を探す。部分読み込みが多いファイルは、索引から独立して復元できる単位を取得する。ブロックをまたぐ共有・循環参照の扱いを、部分復元を採用する条件として確定する。 [参照保持仕様](../WireFormat.md#L112) · [RandomAccess.ReadAsync](https://learn.microsoft.com/en-us/dotnet/api/system.io.randomaccess.readasync)

## 影響範囲

最初の試作は `ApexPack.Core` の既存のバッファ経路、固定長配列の読み取り、比較用ベンチマークが対象。フレームは通信・ストリーム用の入口、ファイル索引と圧縮は必要な利用経路を対象とする。MemoryPack互換層に展開する場合は、配列形式と既存のストリームAPIの契約を別途照合する。

## 移行手順

1. 現行経路の基準値と出力バイト列を保存する。
2. 直接書き込みと固定長配列の分割読み取りを個別に試作し、変更前後の性能と往復結果を比較する。
3. 通信で最初の1件までの時間とピークメモリに課題が残る場合は、長さ付きフレームを明示的に選べる入口として試す。
4. 圧縮やファイル索引は対象の負荷で効果を確認してから、それぞれ採用可否を判断する。

## テスト計画

- 代表入力は10万要素の `int[]`、約1 MiBの複数 `byte[]` を持つデータ、小さいメッセージの連続送信。全件と一部分だけの読み出しを両方測る。 [StreamTest](../../tests/MemoryPack.Upstream/DeserializeTest.cs#L16) · [WriterTest](../../tests/MemoryPack.Upstream/WriterTest.cs#L107)
- 既存形式の出力をバイト単位で照合し、旧データの復元と往復結果を比較する。対象はnull、空、固定長要素内のセグメント境界、不正長、途中切れ。フレーム試作では連続した2件、上限超過、途中の取消、受信側の処理が遅い場合も確認する。
- 同一ランタイム、Release、同じ入力で変更前後を交互に測る。記録するのは復元完了までの時間、初回復元の遅延、p95、割り当て量、ピークメモリ、転送・読み出し量。ネットワークでは実際の接続を使い、ファイルはキャッシュの有無と永続化の条件を揃える。MemoryPackと比べるときも同じ境界と条件で測る。
- 代表ケースで効果と互換性を確認した候補は、標準テストとMemoryPack公式テスト比較で回帰を確認する。公式比較の `StreamTest` はメモリ上の入力から復元する時間を記録しているため、I/Oを含む結果は別に取得する。 [公式比較の計測コード](../../tests/Upstream.Harness/Recorder.cs#L222)

## リスクと対策

- 分割入力の処理が小配列の負担になり得る。連続入力用の経路を対照に含め、サイズごとの損益分岐点を測る。
- 受信側がフレーム全体を保持したまま待つと、送信側がPipeのバッファ上限で停止し得る。受信済み部分の消費、最大フレーム長、途中で失敗した接続の扱いを試作で確認する。
- 圧縮でCPU時間とピークメモリが増えることがある。圧縮済みデータを含めて測り、展開後のサイズにも上限を設ける。索引付きファイルでは、途中で書き込みが止まったときに読み手へ公開できる範囲を定義する。

## 未決事項

- 分割読み取りを選ぶサイズ、フレーム長の上限、送信をまとめる条件。
- 最初の通信試作に使う実ワークロードと評価する回線条件。
- 圧縮方式、ファイル索引の粒度、ブロックをまたぐ参照の扱い。
- 性能改善の採用基準。小さい入力での回帰とメモリ削減の価値を含め、測定結果から判断する。
